------------------------------------------------------------
1. Three approaches
------------------------------------------------------------

Approach A — In-memory fingerprint + TTL window
Build a composite key (e.g. userId|amount|merchantId|roundedTimestamp)
and store it in a Map/Set with expiry (sliding or fixed window, e.g. 2–5 minutes).
On each event: compute key → if present and not expired → duplicate;
else store with timestamp and periodically prune.

Trade-offs:
  + Very fast and simple for a single Node process
  - Lost on restart; weak across multiple instances
  - Clock skew and "same payment later" need careful windowing


Approach B — Idempotency key (client/provider) + Redis
Require or derive an idempotency key (paymentId / provider txn id / client token).
Use Redis SET key NX EX ttl (or SETNX + TTL).
If set fails → duplicate.
Optionally store status (processing / succeeded) for retries.

Trade-offs:
  + Strong for multi-instance and restarts; industry-standard for payments
  - Needs Redis (or equivalent)
  - Depends on a stable unique key; without a provider id you must define
    a safe fingerprint


Approach C — Event log + async dedup (stream/queue)
Append every txn to a stream (Kafka/NATS/Redis Streams).
A consumer maintains a dedup store (DB unique constraint or Redis)
and emits only first-seen events.
Use unique DB index on (providerTxnId) or fingerprint.

Trade-offs:
  + Best for high volume, replay, audit
  - Higher latency and ops cost
  - Overkill for a small single-service app; more moving parts

3. Final recommended solution (B) — JavaScript pseudocode
------------------------------------------------------------

  // Redis-backed idempotent duplicate detector
  async function handlePayment(txn, redis) {
    // Prefer provider/client idempotency key; fallback fingerprint
    const key =
      txn.idempotencyKey ||
      txn.providerTxnId ||
      [
        txn.userId,
        txn.amount,
        txn.currency,
        txn.merchantId,
        // bucket time to absorb minor clock jitter (e.g. 60s)
        Math.floor(txn.occurredAtMs / 60_000),
      ].join("|");

    const redisKey = `pay:idem:${key}`;
    const ttlSec = 24 * 60 * 60; // retain long enough for retries/webhooks

    // SET NX EX: first writer wins
    const created = await redis.set(redisKey, "processing", "EX", ttlSec, "NX");

    if (created !== "OK") {
      return { status: "duplicate", key };
    }

    try {
      const result = await processPayment(txn); // charge / persist / etc.
      await redis.set(redisKey, "succeeded", "EX", ttlSec);
      return { status: "accepted", result };
    } catch (err) {
      // Allow careful retry policy: delete or mark failed with short TTL
      await redis.set(redisKey, "failed", "EX", 60);
      throw err;
    }
  }


------------------------------------------------------------
4. Confidence explanation
------------------------------------------------------------
Recommendation: Approach B (idempotency key + Redis).

Chosen because it stays consistent across the alternatives' strengths:
A's real-time check speed, C's durability/multi-instance needs, without
C's full streaming stack.

Payments commonly retry (client double-submit, webhook redelivery);
Redis SET NX gives an atomic "first seen" guarantee that in-memory Maps
cannot across processes.

Confidence: HIGH when a stable idempotencyKey / providerTxnId exists.
If only a heuristic fingerprint is available, confidence drops to MEDIUM
and the time-bucket fingerprint should be treated as a safety net,
not a perfect identity.
